# multichat audit — jun 2026

> 9-agent audit of src/multichat against the bar: beat chatterino + 7TV + native, never need a manual refresh.

## verdict

This is already a strong multichat — past chatterino on resilience (id-dedup, watchdog rejoin, zero-flicker soft-nav, cross-platform identity, server-side search) — but the retention gate ("never needs a refresh") is breached by a cluster of verified SPA-navigation and watchdog-leak bugs that all surface as the exact "is it broken or just empty?" confusion mellen reports. I verified the top findings in source: soft-nav (main.js:13152/13246) drops the live cache but never re-joins IRC/Kick or re-renders, so a channel switch freezes on the previous channel until an unrelated render fires (deadlock on a quiet/offline target); the YouTube watchdog's ytChanLastSeen is never deleted anywhere in the tree (grep: zero hits), so an ended stream or removed channel re-subscribes forever and eventually force-reconnects the shared WS that every channel rides; irc.part fires only from removeChannel, so all-day channel-hopping leaks a 3000-msg buffer + a zombie BG socket per visited channel; and eswCleanup is absent from the lifecycle abort handler. Fix the nav/render transition and the watchdog-state lifecycle first — those are the difference between "excellent demo" and "daily driver that survives an 8-hour session." Everything else (validation, keyboard nav, numeric badges, chat-mode bar) is real but secondary to making navigation and memory bulletproof.

## ship now (ranked bugs)

### #1 [critical] soft-nav never re-joins or re-renders the live channel — panel freezes on previous channel until refresh
- **files:** `src/multichat/main.js:13152-13239 (softTwitchNav), 13246-13301 (softKickNav), 8581-8582 (lazy join inside render)`
- **why:** VERIFIED: both soft-nav fns call _dropTabCache('live') and reset scroll but make no irc.join/kickChat.join/renderMessages('live') call. The only live-channel join is the lazy guard at 8581-8582 inside renderMessages('live'), which soft-nav never invokes. New channel never joins -> no messages -> the message-handler's `if(currentTab==='live') renderMessages('live')` (12288/12362) never fires -> deadlock. Old channel's messages stop matching isLiveChannelMessage so they stop appending too. mcInitialized stays true so init() can't recover. On a quiet/offline new channel there is ZERO recovery — exact 'needs a refresh' symptom, highest user-impact, the #1 retention killer.
- **action:** At the end of softTwitchNav/softKickNav (and the YT branch), after the cache drop, if currentTab==='live' force the live channels to (re)join via getLivePlatformNames() then call renderMessages('live'). Cleanest: a single authoritative `navigateToLiveChannel(newCh)` transition that parts the old live channel, joins the new, and renders — call it from handleMcNav, don't leave join as a lazy side-effect of render. Verify by switching to an OFFLINE channel and confirming the panel clears without a manual refresh.

### #2 [high] YT watchdog never clears ytChanLastSeen — ended/removed streams re-subscribe forever and force-reconnect the shared WS
- **files:** `src/multichat/main.js:12847-12879 (watchdog), 9133-9160 (removeChannel), 9420-9440 (rename), 13332-13390 (soft-nav YT teardown); social.js:773-775 (ended handler)`
- **why:** VERIFIED: grep for ytChanLastSeen.delete/.clear returns ZERO hits across the whole tree — the map is only ever set. So when a YT stream ends (social.js:773 just sets dataset.live='false'), the watchdog keeps the frozen entry and after 180s fires forever: re-subscribe -> unsub+sub -> ws_force_reconnect (background.js:5425 tears down the ENTIRE socket and replays every Twitch/Kick/YT join), then loops. removeChannel deletes youtubeLinks/channelYtMessages but NOT ytChanLastSeen/ytChanRejoinAttempts/ytSubscribedUrls, so deleted channels also resurrect. Soft-nav leaves __live_yt_auto__ stale so the previous page's YT chat bleeds back. One ended stream periodically nukes the WS all channels ride — directly causes intermittent 'everything dropped, refresh fixed it'.
- **action:** On youtube_status 'ended'/terminal-error in social.js, delete ytChanLastSeen/ytChanRejoinAttempts/ytSubscribedUrls for that id. Add the same three deletes to removeChannel (after the YT unsub block), to the rename key-migration at 9440, and to both soft-nav branches for '__live_yt_auto__' and each per-channel id. Watchdog should only arm channels still expected live.

### #3 [high] SPA channel-hopping leaks a 3000-msg buffer + a zombie BG socket per channel — unbounded over an 8h session
- **files:** `src/multichat/main.js:13152-13238 (softTwitchNav), 13246+ (softKickNav), 9133-9143 (only part() caller); irc.js:462-529 (join/part, CircularBuffer 3000)`
- **why:** VERIFIED: irc.part/kickChat.part are called ONLY from removeChannel (explicit delete), never on nav. irc.channels/kickChat.channels are plain Maps with no LRU/cap. Soft-nav joins the new channel lazily but never PARTs the old one, and bg_irc_join is never balanced by bg_irc_part on nav. Hopping 30-50 streams over 8h = tens of thousands of retained msg objects client-side + dozens of zombie IRC/Kick subscriptions BG-side. Violates the project's own <50MB/8h perf rule on passive-cooled hardware — the second-biggest 'needs a refresh' driver (slow memory bloat).
- **action:** On soft-nav, track _lastLiveJoined and PART the old live channel if it isn't a configured/pinned tab: `if(_lastLiveJoined && _lastLiveJoined!==newCh && !config.channels.some(c=>c.twitch?.toLowerCase()===_lastLiveJoined)) irc.part(_lastLiveJoined)` (mirror for kick). Or add an LRU cap on irc.channels/kickChat.channels keeping configured tabs + N most-recent. Fold this into the rank-1 navigateToLiveChannel transition so join+part+render are one atomic step.

### #4 [high] no pageshow/bfcache handler — back/forward restores a dead panel
- **files:** `src/multichat/bootstrap.js:58 (pagehide -> lifecycle.abort()), chrome/content.js:83 (same)`
- **why:** VERIFIED: pagehide unconditionally aborts (disconnects observers, destroys IRC/Kick, deletes all _hsMc* flags) with no event.persisted check, and grep finds no pageshow/persisted handler anywhere. On bfcache restore Chrome brings back the orphaned panel DOM wired to nothing — IRC dead, observers gone, init() never re-runs. Clicking a chat link then hitting Back leaves a visible-but-dead panel needing a manual refresh. Native/chatterino don't have this class of bug; an SPA content-script must handle bfcache to honor 'never refresh'.
- **action:** Guard teardown on real unloads only: `pagehide, e => { if(!e.persisted) lifecycle.abort() }`, and add a pageshow handler that re-validates / re-inits on `e.persisted` (light re-init path preferred over a hard location.reload). Verify by navigating away and pressing Back, confirming the panel sends/receives without refresh.

### #5 [high] Kick back-button/programmatic nav can leave the panel permanently removed (null container, no recovery)
- **files:** `src/multichat/main.js:13447-13472 (click-capture migrate, click-only), 13247 & 13276-13288 (softKickNav/tryReparent re-read getElementById, stays null forever)`
- **why:** The pre-emptive migrate that saves the panel from Kick's React teardown runs ONLY on a primary-button click of an eligible anchor — popstate (Back/Forward) and programmatic navs (category->streamer, JS redirects) never hit it. kick-nav-watcher's own comment notes React tears down #channel-chatroom BEFORE pushState. For those navs the container is already gone when softKickNav runs: getElementById returns null, the reparent is skipped, tryReparent re-reads the same null forever, the 4s observer gives up, panel never returns. Twitch shares the same unhandled null-container failure on chat-shell teardown transitions (home->channel, directory->channel), lower frequency.
- **action:** Make softKickNav AND softTwitchNav self-healing: if getElementById('hs-mc-container') is null after nav, rebuild via ensureUIElements()/the init mount path instead of no-op. Add a popstate-triggered pre-emptive migrate (or migrate on the heatsync-nav event before React commits). Verify Kick category->streamer + Back rebuilds the panel.

### #6 [high] YouTube video->video nav (same /watch pathname) never triggers soft-nav — wrong video's chat persists
- **files:** `src/multichat/main.js:13304 (`if(location.pathname===lastPath) return`), 13332-13366 (YT branch), 9687-9688 (channel id from ?v=)`
- **why:** handleMcNav early-returns on unchanged pathname, but YouTube identifies the video by ?v= and the pathname is /watch for every video. So /watch?v=A -> /watch?v=B skips the entire YT soft-nav block (auto-YT unsubscribe, channelYtMessages.delete, scroll reset). The yt-navigate-finish listener and the 5s polling fallback both route through handleMcNav so they're equally gated and can't rescue it. Previous video's chat sticks until a hard refresh. content.js gates on location.href so the two sides are already inconsistent.
- **action:** Gate handleMcNav on a fuller per-platform nav-key: YouTube = pathname+location.search (or specifically ?v=), Twitch/Kick = pathname. Compare against lastNavKey instead of lastPath. Best done as a shared nav-key helper used by both content.js and main.js to also kill the href-vs-pathname asymmetry. Verify by switching between two live YT streams without refresh.

### #7 [high] Kick periodic live-status poll never queries Kick — Kick live dots go stale/wrong every 90s
- **files:** `src/multichat/main.js:9566-9619 (updateLiveStatus), interval 9537, 11682-11695 (checkKickLive add-only)`
- **why:** VERIFIED via grep: the periodic poll at 9593 sends only {channels} (twitch); kickChannels is passed only in the on-demand picker at 9932, never in the 90s loop. updateLiveStatus builds allChannels as ch.twitch||ch.id, so a Kick-only entry's slug is sent as a Twitch name and returns not-live; line 9608 rebuilds liveChannelSet every 90s, wiping any Kick entry the DOM poll added at 11687. Net: a Kick channel's live dot is correct only if the user FOLLOWS it on heatsync — ad-hoc Kick channels flicker off every 90s. checkKickLive is also add-only and never clears on stream end. Pure 'is it live or broken?' ambiguity on every Kick tab.
- **action:** In updateLiveStatus split config.channels into twitch + kick name lists (mirror the picker at 9919-9926), pass both channels and kickChannels to fetch_live_status, merge resp.kickLive into liveSet, and stamp dots checking BOTH ch.twitch and ch.kick (as applyLiveDotsFromCache already does). Make checkKickLive authoritative both directions (delete on !isLive). Skip names already in _swLiveSet to keep the quota optimization.

### #8 [high] getCurrentChannel regex truncates hyphenated Kick slugs — live tab, routing, and dot all break for those channels
- **files:** `src/multichat/main.js:9695 (also 10164, 11788)`
- **why:** The regex `/^\/(?:popout\/|embed\/)?([a-zA-Z0-9_]+)/` omits hyphen, but the rest of the codebase treats Kick slugs as hyphen-bearing (background.js:3925 validates [a-zA-Z0-9_-]{1,25}, watching-tab regex 5267, segMatch 13020). Kick allows hyphens in slugs. On kick.com/some-streamer getCurrentChannel returns 'some' — so the live tab, message routing, and live dot all silently target the wrong/nonexistent channel. Silent breakage for an entire class of Kick channels with no error.
- **action:** Change the class to [a-zA-Z0-9_-]+ at 9695, 10164, 11788. Twitch logins are [a-zA-Z0-9_] so adding '-' is harmless there. Better: extract one shared hyphen-safe slug helper to kill the 5 divergent inline regexes that caused this drift.

### #9 [high] no channel-existence validation on add (any platform) — typos create permanent silent dead tabs
- **files:** `src/multichat/main.js:9001-9052 (doAdd), 9003-9051; irc.js:462-463 (join only lowercases)`
- **why:** Consolidated from 3 reports (Twitch fetch, Kick fetch, add-UX). doAdd validates only emptiness/reserved/duplicate. Twitch field does trim/lowercase/strip-@ then irc.join, which joins ANY string incl. typos, names with spaces, or a pasted twitch.tv/xqc URL — creating a permanent tab that forever shows nothing with zero feedback. Only YouTube parses URLs (normalizeYtUrl); twitch/kick parse nothing. The autofill resolver result (res.ok/res.notFound) is computed but purely advisory, never gates submit. This is a primary source of the 'broken or just empty?' confusion at the very first interaction.
- **action:** On submit, resolve each non-empty platform name (reuse the autofill resolveIdentity / resolveTwitchChannelId path) and gate the push on a real id. Add parseTwitchLogin/parseKickSlug to strip platform-URL forms and validate charset (twitch [a-z0-9_]{4,25}, kick [a-z0-9_-]{1,25}); auto-extract slug if a URL is pasted into the wrong field; maxlength on inputs; backstop-sanitize in irc.js:463. If a name doesn't resolve, inline-warn under the field + require confirm-anyway, and distinguish 'not found' (bad name) from 'offline' (real account, not live) in the resulting tab's empty state.

### #10 [medium] YT normalizeYtUrl passes through unresolvable URL forms AND the resolve failure is silenced — zero feedback
- **files:** `src/multichat/main.js:2233-2249 (normalizeYtUrl); social.js:820-836 (isNoise suppression)`
- **why:** normalizeYtUrl only canonicalizes bare-name, ?v=, /live/ID, youtu.be/ID. Pasting any other valid YT channel URL (/channel/UC…, /@name without /live, /c/, /user/) is handed to the server unchanged; when it can't resolve, status 'error' with 'could not resolve youtube url' is classified isNoise at social.js:825 and shows NOTHING. Combined with no add-time liveness check, a YT-only add produces a permanently dark yt-<timestamp> tab with no explanation — the worst false-done failure mode for the user.
- **action:** Extend normalizeYtUrl to map /channel/UC…, /@name, /c/name, /user/name to the canonical form the server resolver accepts. In social.js do NOT suppress 'could not resolve' for explicit per-channel (non-__live_yt_auto__) subscriptions — show 'youtube: couldn't find a live stream for that url/handle'; keep suppression only for the auto-from-twitch guess. Add a transient 'youtube: connecting…' notice + 12s timeout that flips to 'no live stream found'.

### #11 [medium] EventSub whisper WS + keepalive not torn down on lifecycle.abort()
- **files:** `src/multichat/bootstrap.js:45 (abort calls cleanupAuthIrc but no eswCleanup); eventsub-whispers.js:94-108 (eswCleanup), 228-231 (onclose -> reconnect)`
- **why:** VERIFIED: bootstrap.js abort handler calls cleanupAuthIrc(true) at line 45 but never eswCleanup(true); grep confirms eswCleanup/eswState are referenced only inside eventsub-whispers.js. On re-injection (extension update/reload fires abort) the old IIFE's eswState.ws stays OPEN with destroyed=false; when it later closes, onclose spins a fresh reconnect timer against the dead closure, keeping the whole prior IIFE alive. Asymmetric teardown that leaks a live socket + reconnect machinery per update cycle.
- **action:** Add `try { eswCleanup(true) } catch {}` to the mcSignal abort handler in bootstrap.js right next to cleanupAuthIrc(true) at line 45. eswCleanup(true) already sets destroyed=true, clears keepalive/reconnect/oldWs timers, and closes the socket.

### #12 [medium] mentions.js title-flash listeners leak one pair per re-injection (untracked + guard wiped)
- **files:** `src/multichat/mentions.js:137-143; bootstrap.js:52-56 (wildcard _hsMc* delete)`
- **why:** focus + visibilitychange listeners are registered with NO {signal: mcSignal} and no cleanup.addEventListener, install-once-guarded by window._hsMcTitleFlashFocusWired. The abort handler wildcard-deletes every _hsMc* key WITHOUT removing these two listeners (they aren't signal-tracked). On next re-injection the guard is gone so both re-add while the old pair stays attached forever, each capturing the dead old-IIFE closure. +1 focus +1 visibilitychange leaked per re-injection plus the whole prior IIFE held alive.
- **action:** Register both through the lifecycle: `addEventListener('focus', _titleFlashStop, {signal: mcSignal})` and `addEventListener('visibilitychange', …, {signal: mcSignal})`, so abort removes them in lockstep with wiping the guard.

### #13 [medium] multi-platform tabs sort the full 1500-per-platform buffer every animation frame
- **files:** `src/multichat/main.js:8220-8228, 8357-8391 (fairMerge), 8395 (byTimeStable), 8628`
- **why:** This is the exact '4+ busy chats' scenario. appendMessage early-exits on 2+ platforms and schedules a full renderMessages; fairMerge pulls each source via getAll() (the entire 1500 ring), concatenates to ~3000-4500 items, and pool.sort(byTimeStable) runs ~60x/sec, with byTimeStable calling stableMsgId (string concat) on both operands per comparison — tens of thousands of string allocations/sec. Only slice(-500) is kept so >80% of the work is discarded. Real CPU waste on passive-cooled hardware; not a crash but a perf-is-a-feature miss on the headline use case.
- **action:** In fairMerge pre-slice each source to ~DOM_RENDER_CAP newest before concatenating (ring buffers are already chronological so slice(-limit) is safe/cheap) — sort at most active*limit items, not active*1500. Cache stableMsgId on the message (m._sid) the first time so the comparator stops rebuilding the string every frame.

### #14 [medium] join-timeout on a healthy socket can strand a queued send until the next manual send
- **files:** `src/multichat/auth-irc.js:246-263 (joinChannel 2s timeout), 300-309 (queue+toast), 265-276 (drainSendQueue only on reconnect)`
- **why:** joinChannel resolves false after 2s; sendIrcMessage then queues + toasts 'queued', but there's no background retry of the JOIN itself — drainSendQueue fires only on a full reconnect. If the socket stays OPEN but a single channel's JOIN was merely slow (not a disconnect), the queued message sits until the next manual send or a reconnect that may never come. The user's message silently never sends — a data/intent-loss feel even if not corruption.
- **action:** When a send is queued due to join-timeout on a live socket, schedule a one-shot re-JOIN + drainSendQueue (retry JOIN 2-3s up to N times) rather than relying solely on reconnect. Or route queued-on-join into the same persistent retry notif used for no_echo so the user can manually retry.

## best-in-class roadmap

- keyboard tab navigation — alt+1..9 to jump to the Nth channel, alt+[ / alt+] or ctrl+pgup/pgdn to cycle, alt+0 to feed; ~30 lines via a cleanup-tracked keydown guarded against typing in the input, mapped over the existing scrollable-tab NodeList. Biggest ergonomic miss vs chatterino and a direct hit against mellen's keyboard-first directive
- numeric per-tab unread + mention counts (not just a dot) — track a per-tab unread counter (increment in appendMessage when tab!==currentTab, reset on switchTab) and a mention counter (detection already in mentions.js); render a small right-aligned mono count capped at 99+, fits the square/dense aesthetic
- per-channel chat-connection health on the tab + inline 'reconnecting #channel…' line when a watchdog fires (irc.js:635 already knows the channel) — reflect WS/IRC socket state distinct from stream-liveness; directly kills the 'broken or just quiet?' ambiguity that is the stated top concern
- keyword highlights with per-phrase color + sound + title-flash — wire the existing mention synth (mentions.js:76-91) and mentionTitleFlash into the keyword-match path (main.js:7879, currently CSS-class only), and extend the highlights schema to per-line #rrggbb/!sound suffixes (settings-schema.js:347 already stores free text)
- followed-and-live discovery list in the add form + live-tab empty state — one-click 'add' per live followed channel using the SW followed snapshot (liveChannelSet / refresh_followed_users); turns the teased 'live on t,k' into action and makes first-run non-empty
- merged firehose 'all' tab interleaving every configured channel by byTimeStable with a per-line channel pill (showPlatformBadges infra exists) — opt-in behind a setting for low-RAM; lets mellen watch his many small chats as one river (his actual daily multichat use)
- self-healing 'ensure panel exists' watchdog — a low-frequency interval (or reuse columnObserver at main.js:6284) that detects a missing/orphaned #hs-mc-container after any nav and rebuilds it, so no navigation path can ever permanently lose the panel even if a specific soft-nav case is missed
- route all Kick reads through heatsync.org's official Kick API + webhooks with a server-fetched Pusher app-key/cluster behind a remote kill-switch — removes the policy-violating private kick.com/api/v2 + hardcoded rotating Pusher key (background.js:8250-8361) as single points of failure; add health telemetry distinguishing 'pusher key dead' from 'channel quiet' so silent Kick failures surface instead of looking like 'needs a refresh'
- YT self-resolution fallback — when the server can't resolve a URL, derive the live videoId client-side via the already-permitted oEmbed/innertube path (background.js already does oEmbed) instead of dead-ending the add
- drag-to-reorder tabs (pointer-based, no animated slide) + move-up/down in channel settings, persisting config.channels order
- split / multi-pane simultaneous view — render N channel buffers side by side; chatterino's signature feature and the largest remaining structural gap to 'best in existence'
- jump-to-message from the search panel into live chat context, plus a per-tab activity sparkline so a glance shows which channel is popping off
